# Архитектурный анализ BookStoreCRM

Дата анализа: 21 июля 2026 г.

## 1. Область и метод анализа

Проведён статический анализ solution-файла, файлов проектов, направлений зависимостей, исходного кода Domain/DAL/BLL/Web, конфигураций Entity Framework Core, миграций, регистрации зависимостей, MVC-контроллеров, моделей представления, middleware и файловых сервисов.

Исходный код не изменялся. Сборка и автоматические тесты не запускались, чтобы не обновлять каталоги `bin` и `obj`. Поэтому выводы о компиляции и поведении во время выполнения основаны на статическом анализе.

## 2. Краткое резюме

BookStoreCRM — ASP.NET Core MVC-приложение на .NET 8, разделённое на четыре проекта: Domain, DAL, BLL и Web. Базовое разделение ответственности узнаваемо и подходит для небольшого учебного приложения. Основной поток вызовов выглядит как `Web -> BLL -> DAL -> Domain`.

Архитектура не является строго изолированной N-tier/Clean Architecture:

- Domain зависит от ASP.NET Core Identity Entity Framework Core;
- BLL напрямую зависит от DAL;
- Web фактически использует DAL и Domain через транзитивные ссылки;
- логика управления аккаунтом разделена между Web и BLL;
- один из интерфейсов BLL раскрывает сущности Domain наружу.

Кроме архитектурных отклонений обнаружены важные практические проблемы: отсутствие авторизации у административного контроллера заказов, пароль seed-администратора в исходном коде, потенциально небезопасное удаление файла по пути из HTTP-модели, неверный первичный ключ позиции заказа и ошибка обработки невалидной модели при создании книги.

## 3. Состав solution

В `BookStoreCRM.sln` находятся четыре проекта.

| Проект | Тип | Target framework | Ответственность |
|---|---|---:|---|
| `BookStoreCRM.Domain` | Class Library | `net8.0` | Сущности, перечисления и константы предметной области |
| `BookStoreCRM.DAL` | Class Library | `net8.0` | EF Core, SQL Server, DbContext, конфигурации, миграции, репозитории, Unit of Work |
| `BookStoreCRM.BLL` | Class Library | `net8.0` | Сервисы приложения, DTO, mapping и прикладные исключения |
| `BookStoreCRM.Web` | ASP.NET Core Web | `net8.0` | MVC-контроллеры, Razor Views, ViewModel, авторизация, middleware и файлы |

Отдельных проектов для unit-, integration- или architecture-тестов нет.

## 4. Назначение слоёв

### 4.1. Domain

Domain содержит:

- сущности `Books`, `Categories`, `Orders`, `OrderItems`, `Reviews`, `Wishlists`, `FriendRequests`, `ApplicationUsers`;
- базовый идентификатор `BaseEntity.Id`;
- перечисления статуса заказа и запроса в друзья;
- константы ролей Admin, Manager и Customer.

Положительная сторона — модель предметной области собрана отдельно от MVC и DAL. Однако `ApplicationUsers` наследуется от `IdentityUser<Guid>`, а проект содержит пакет `Microsoft.AspNetCore.Identity.EntityFrameworkCore`. Таким образом, Domain связан с конкретным механизмом идентификации и инфраструктурой ASP.NET Core/EF Core.

### 4.2. DAL

DAL содержит:

- `AppDbContext`, наследуемый от `IdentityDbContext`;
- Fluent API-конфигурации всех основных сущностей;
- EF Core migrations и snapshot;
- обобщённый и специализированные репозитории;
- `IUnitOfWork` и `UnitOfWork`;
- провайдер SQL Server.

DAL корректно зависит от Domain и не имеет ссылок на BLL или Web. Это правильное направление для классической слоистой архитектуры.

### 4.3. BLL

BLL содержит:

- интерфейсы и реализации сервисов книг, категорий, заказов, отзывов и аккаунтов;
- DTO для входных и выходных данных;
- AutoMapper-профиль преобразования Domain entity в DTO и обратно;
- исключения `ValidationException`, `NotFoundException`, `ConflictException`.

Сервисы координируют репозитории через Unit of Work и сохраняют изменения. Бизнес-логика пока сравнительно тонкая: в основном получение сущностей, mapping и CRUD. Значительная часть проверок находится только в Web ViewModel, а не в BLL, поэтому BLL нельзя считать полностью самостоятельной границей валидации.

### 4.4. Web

Web является MVC-приложением и composition root. Он содержит:

- публичные и административные контроллеры;
- Razor Views и ViewModel;
- регистрацию DbContext, Identity, репозиториев, Unit of Work и BLL-сервисов;
- AutoMapper-профиль DTO/ViewModel;
- глобальное middleware обработки исключений;
- seed ролей и администратора;
- сервисы загрузки, проверки и удаления изображений.

Регистрация инфраструктуры в точке запуска допустима. Проблема состоит в том, что Web формально ссылается только на BLL, хотя напрямую компилируется против DAL и Domain благодаря транзитивным project references.

## 5. Граф зависимостей

### 5.1. Формальные ProjectReference

```text
BookStoreCRM.Web
        |
        v
BookStoreCRM.BLL ------> BookStoreCRM.Domain
        |
        v
BookStoreCRM.DAL ------> BookStoreCRM.Domain
```

- Domain: нет project references.
- DAL: ссылка на Domain.
- BLL: ссылки на DAL и Domain.
- Web: ссылка только на BLL.

### 5.2. Фактическое использование

Фактический граф шире:

- Web использует классы BLL;
- `Program.cs` напрямую использует `AppDbContext`, интерфейсы и реализации репозиториев, `IUnitOfWork` и `UnitOfWork` из DAL;
- Web-контроллеры, seed и ViewModel используют `ApplicationUsers`, `Roles` и `OrderStatus` из Domain;
- BLL использует `IUnitOfWork` и репозитории из DAL;
- BLL использует сущности, роли и перечисления Domain;
- DAL использует сущности Domain.

Транзитивность project references позволяет этому коду собираться, но скрывает реальные зависимости в файле `BookStoreCRM.Web.csproj`.

## 6. Оценка соответствия N-tier

### 6.1. Что сделано правильно

- Нет обратных ссылок DAL на BLL/Web или Domain на BLL/Web.
- Web-контроллеры для основных CRUD-сценариев обращаются к BLL-сервисам, а не непосредственно к DbContext.
- DTO BLL отделены от ViewModel Web.
- EF Core mapping и migrations находятся в DAL.
- MVC-специфичные типы сосредоточены преимущественно в Web.
- Глобальные прикладные исключения BLL переводятся Web-слоем в HTTP-статусы.

### 6.2. Нарушения и компромиссы

#### Domain зависит от Identity/EF Core

`BookStoreCRM.Domain.csproj` содержит `Microsoft.AspNetCore.Identity.EntityFrameworkCore`, а `ApplicationUsers` наследуется от `IdentityUser<Guid>`. Чистый Domain не должен зависеть от persistence/web-фреймворка. В классическом N-tier это может быть осознанным компромиссом; в Clean Architecture это нарушение внутреннего направления зависимостей.

#### BLL зависит от DAL

BLL ссылается на DAL и использует `IUnitOfWork`, объявленный в DAL. Для традиционного `Presentation -> Business -> Data Access` это допустимо, но нарушает Dependency Inversion. При более строгом подходе абстракции persistence должны принадлежать Application/BLL, а DAL должен реализовывать их.

#### Web неявно зависит от DAL и Domain

`Program.cs` напрямую регистрирует DAL-типы, однако `BookStoreCRM.Web.csproj` не содержит явной ссылки на DAL. Зависимость доступна транзитивно через BLL. Это ухудшает читаемость архитектуры и позволяет любому Web-коду незаметно обходить BLL.

#### Identity-сценарии распределены между слоями

`AccountService` выполняет регистрацию, но `AccountController` напрямую использует `UserManager<ApplicationUsers>` и `SignInManager<ApplicationUsers>` для входа, проверки ролей и последующего входа после регистрации. Граница BLL получается неполной и непоследовательной.

#### BLL API раскрывает Domain entity

`IReviewService.DeleteAsync(Reviews review)` и `GetByIdAsync` передают `Reviews` наружу. Web получает внутреннюю EF/Domain-модель вместо DTO или операции `DeleteAsync(Guid id)`. Это связывает presentation с внутренним представлением данных.

## 7. Обнаруженные проблемы

### 7.1. Критический приоритет

#### SEC-01. Жёстко задан пароль администратора

`BookStoreCRM.Web/Seed/IdentitySeeder.cs` создаёт `admin@bookstore.com` с паролем `Admin123`, записанным непосредственно в исходном коде.

Риски:

- одинаковые известные credentials во всех окружениях;
- автоматическое появление привилегированной учётной записи;
- пароль может попасть в репозиторий, историю и опубликованную сборку.

Рекомендация: получать начальные credentials из Secret Manager/переменных окружения, требовать смену пароля и не создавать стандартного администратора в production без явной настройки.

#### SEC-02. Потенциальный выход за пределы `wwwroot` при удалении файла

`BookController.Edit` передаёт `model.ImageUrl` в `FileService.DeleteAsync`. Значение модели приходит из HTTP-запроса и может быть подменено. `DeleteAsync` объединяет `WebRootPath` с этим относительным путём, но не проверяет канонический результат и наличие его внутри разрешённого каталога.

Злоумышленник с доступом к операции редактирования теоретически может передать путь с `..` и удалить доступный процессу файл вне каталога загрузок. Авторизация снижает доступность атаки, но не устраняет дефект.

Рекомендация: получать старый путь из БД по `Id`, принимать от клиента только новый файл, вычислять `Path.GetFullPath`, проверять принадлежность разрешённому upload-root и хранить только контролируемое имя файла.

### 7.2. Высокий приоритет

#### AUTH-01. `OrderController` в Admin Area не защищён

`BookStoreCRM.Web/Areas/Admin/Controllers/OrderController.cs` имеет `[Area("Admin")]`, но не имеет `[Authorize]`, в отличие от Home, Book, Category и Review controllers. В результате список заказов и их детали, включая данные покупателя, могут быть доступны неавторизованным пользователям по административному маршруту.

Рекомендация: применять общую policy/authorization convention ко всей Admin Area, чтобы защита не зависела от атрибута на каждом контроллере.

#### DATA-01. Неверный первичный ключ `OrderItems`

`OrderItems` наследует `BaseEntity` и имеет собственный `Id`, но `OrderItemsConfiguration` задаёт `HasKey(oi => oi.OrderId)`. Это подтверждается initial migration: первичный ключ таблицы `OrderItems` состоит только из `OrderId`.

Следствие: один заказ физически может иметь не более одной позиции, несмотря на коллекцию `Orders.OrderItems`. Попытка добавить вторую книгу в заказ приведёт к конфликту ключа.

Рекомендация: использовать `Id` как первичный ключ либо осознанный составной ключ `{ OrderId, BookId }`, затем создать корректирующую migration.

#### WEB-01. Невалидная модель создания книги продолжает обработку

В POST-методе `BookController.Create` при `!ModelState.IsValid` вызывается `LoadCategories(model)`, но отсутствует `return View(model)`. После этого контроллер продолжает загрузку файла, mapping и создание книги.

Следствия:

- серверная валидация обходится;
- возможна запись некорректных данных;
- возможны исключения FK/БД;
- файл может сохраниться до неуспешной записи данных.

#### FILE-01. Файл и запись БД изменяются без общей стратегии согласованности

При create/edit/delete книги файловая система изменяется отдельно от транзакции БД:

- create сначала сохраняет файл, затем создаёт книгу;
- edit сначала удаляет старый файл, затем сохраняет новый и обновляет БД;
- delete сначала удаляет изображение, затем удаляет книгу.

Если следующий шаг завершится ошибкой, останется orphan-файл, потерянное изображение или запись со ссылкой на отсутствующий файл.

Рекомендация: определить compensating actions; при обновлении сначала сохранить новый файл, успешно обновить БД, затем безопасно удалить старый; при ошибке удалить новый файл.

### 7.3. Средний приоритет

#### DI-01. Регистрации репозиториев фактически не используются Unit of Work

`Program.cs` регистрирует все repository interface/implementation пары, но `UnitOfWork` не получает их через конструктор и самостоятельно создаёт реализации через `new ...Repository(_context)`. Эти scoped-регистрации избыточны для текущего потока и создают две конкурирующие модели управления зависимостями.

Рекомендация: либо внедрять репозитории в Unit of Work, либо убрать их отдельные регистрации и оставить Unit of Work единственной точкой доступа.

#### VAL-01. Основная валидация сосредоточена только в Web

ViewModel содержат `[Required]`, `[Range]` и `[StringLength]`, но входные DTO BLL почти не имеют проверок, а сервисы доверяют данным. Другой клиент BLL сможет обойти MVC-валидацию.

Рекомендация: проверять бизнес-инварианты в BLL независимо от presentation; Web-валидацию оставить для удобной обратной связи пользователю.

#### FILE-02. Проверка типа файла неполная и разделена между двумя сервисами

`FileValidator` проверяет наличие и размер, используя константы BLL. Расширение проверяется позднее в `FileService`, использующем отдельную копию констант Web. MIME/signature содержимого не проверяются.

Риски: расхождение списков расширений, исключение вместо ошибки ModelState, загрузка файла с поддельным расширением.

#### WEB-02. При ошибке валидации изображения в Edit не восстанавливаются категории

Когда `_fileValidator.Validate` возвращает false, `BookController.Edit` сразу возвращает View, не вызывая `LoadCategories`. Dropdown категорий может оказаться пустым или отобразиться некорректно.

#### ERR-01. Две конкурирующие схемы обработки исключений

В production подключается стандартный `UseExceptionHandler("/Home/Error")`, после чего всегда подключается custom `UseGlobalExceptionHandling`. Пользовательское middleware перенаправляет путь на `/Error`, а стандартный обработчик — на `/Home/Error`. Это усложняет порядок обработки и может давать разные страницы/статусы в разных окружениях.

#### API-01. Непоследовательные null-контракты BLL

Например, `BookService.GetBookByIdAsync` объявлен как nullable, но при отсутствии книги выбрасывает `NotFoundException`. Вслед за этим контроллер проверяет результат на null, хотя ветка недостижима. `CategoryService.GetByIdAsync`, напротив, может вернуть null. Это затрудняет использование API.

#### SEC-03. Удаление отзыва не защищено antiforgery-атрибутом

POST `ReviewController.Delete` не имеет `[ValidateAntiForgeryToken]`, тогда как операции удаления книг и категорий защищены. Если view также не обеспечивает ожидаемую защиту, возможен CSRF административного действия.

### 7.4. Низкий приоритет и качество структуры

#### NAME-01. Сущности названы во множественном числе

Классы `Books`, `Orders`, `Reviews`, `Categories`, `ApplicationUsers` представляют один объект. Идиоматичные имена — `Book`, `Order`, `Review`, `Category`, `ApplicationUser`. Текущие имена ухудшают читаемость выражений и mapping.

#### NAME-02. Опечатки и непоследовательные имена

- `OrderViewMoel` вместо `OrderViewModel`;
- `MiddlewareExtentions` вместо `MiddlewareExtensions`;
- `AllowedExtentions` вместо `AllowedExtensions`;
- `CategoryRepository` в Unit of Work при интерфейсе `ICategoriesRepository`;
- `Save` лучше обозначить как `SaveChangesAsync`.

#### DUP-01. Дублирование файловых констант

`FileConstants` и `FileFolders` существуют одновременно в BLL и Web. `FileValidator` из Web зависит от BLL-констант, а `FileService` — от Web-констант. Это необоснованно связывает слои и создаёт риск расхождения значений.

#### DAL-01. `DbSet` в AppDbContext закрыты

Свойства `DbSet` не имеют модификатора доступа и поэтому являются private. Текущие репозитории работают через `context.Set<TEntity>()`, так что это не обязательно вызывает ошибку EF Core, но объявления недоступны остальному DAL и выглядят как случайный пропуск.

#### DAL-02. Избыточные using и пакет

В ряде файлов присутствуют неиспользуемые `using` (`System`, collections, threading). В DAL подключён устаревший/сомнительный для прикладного проекта пакет `System.Diagnostics.Tools` 4.3.0, явной необходимости в котором по коду не видно.

#### TEST-01. Нет автоматических тестов

Не проверяются:

- направления project references;
- авторизация Admin Area;
- mapping-профили;
- бизнес-инварианты;
- CRUD и связи EF Core;
- обработка ошибок и файловые операции.

Именно architecture-тест мог бы предотвратить прямое использование DAL из presentation-кода, а integration-тест — выявить невозможность добавить несколько OrderItems.

## 8. Модель данных: дополнительные наблюдения

- Связь Category -> Books настроена с `DeleteBehavior.Restrict`, что защищает от случайного удаления категории с книгами.
- Удаление Book каскадно удаляет Reviews и Wishlists, но ограничивается при наличии OrderItems. Это в целом логично для сохранения истории заказов.
- Для Wishlists не видно уникального ограничения `{ UserId, BookId }`, поэтому одна книга потенциально может быть добавлена пользователем несколько раз.
- Для Reviews не видно уникального ограничения `{ UserId, BookId }`; возможность нескольких отзывов одного пользователя на одну книгу зависит от требований, но сейчас БД её не ограничивает.
- Для FriendRequests не видно ограничения на дублирующиеся активные запросы или запроса самому себе; такие инварианты должны обеспечиваться BLL и/или индексами.
- Для `Grade`, `Quantity`, `Price` и `TotalPrice` не заданы database check constraints. Некорректные значения можно записать в обход MVC.

## 9. Сильные стороны решения

- Понятное физическое разделение на четыре проекта.
- Все проекты используют одинаковый target framework и nullable reference types.
- DAL не зависит от верхних слоёв.
- Репозитории имеют общую базовую реализацию, специализированные запросы вынесены отдельно.
- EF Core-конфигурации разделены по сущностям и применяются автоматически из assembly.
- Контроллеры основных административных сущностей используют интерфейсы BLL.
- DTO и Web ViewModel разделены.
- Присутствуют async-операции доступа к данным.
- Используются antiforgery-токены в большинстве изменяющих MVC-операций.
- Исключения BLL централизованно отображаются в HTTP-статусы.

## 10. Рекомендуемая целевая структура

Для сохранения классического N-tier без крупной переработки достаточно следующего направления:

```text
Web (MVC, Views, Identity UI, Files, Composition Root)
  |
  v
BLL/Application (use cases, DTO, validation, repository abstractions)
  |
  v
DAL/Infrastructure (EF Core, Identity stores, repositories, migrations)
  |
  v
Domain (entities, value objects, enums, business invariants)
```

Предпочтительный вариант с Dependency Inversion:

```text
Web ----------> BLL/Application ----------> Domain
 |                     ^
 |                     |
 +----> DAL/Infrastructure
             |
             +---- implements BLL abstractions
             +---- references Domain
```

Composition root Web может ссылаться на BLL и DAL явно, но контроллеры должны использовать только API BLL. DAL может предоставить `AddDataAccess(...)`, BLL — `AddApplication(...)`, чтобы `Program.cs` не перечислял все внутренние типы.

## 11. Приоритетный план улучшений

### Этап 1 — безопасность и функциональные дефекты

1. Убрать пароль администратора из исходного кода и настроить безопасный bootstrap.
2. Защитить всю Admin Area общей authorization policy.
3. Исправить первичный ключ `OrderItems` и подготовить migration.
4. Добавить немедленный `return View(model)` при невалидной модели создания книги.
5. Исключить использование клиентского `ImageUrl` для выбора удаляемого файла; нормализовать и ограничить пути.
6. Добавить antiforgery-защиту удалению отзывов.

### Этап 2 — устойчивость

1. Обеспечить согласованность файловых операций и транзакций БД.
2. Централизовать validation и файловые настройки.
3. Унифицировать null/exception-контракты сервисов.
4. Оставить один механизм глобальной обработки исключений.
5. Добавить ограничения и индексы для бизнес-инвариантов БД.

### Этап 3 — архитектурные границы

1. Переместить repository/Unit of Work abstractions из DAL в BLL/Application или отдельный abstractions-проект.
2. Закрыть прямой доступ Web-контроллеров к DAL и Domain entities.
3. Сосредоточить полные account use cases в BLL/Application.
4. Решить, должен ли Domain зависеть от ASP.NET Identity; при строгой архитектуре вынести Identity-модель в Infrastructure.
5. Упростить DI-регистрации через методы расширения слоёв.

### Этап 4 — поддерживаемость

1. Добавить unit-, integration- и architecture-тесты.
2. Исправить имена и опечатки отдельным контролируемым refactoring.
3. Удалить дублирующиеся константы, лишние using и неиспользуемые packages.

## 12. Итоговая оценка

| Область | Оценка | Комментарий |
|---|---|---|
| Разделение проектов | Хорошо | Ответственности физически разделены и понятны |
| Направление зависимостей | Удовлетворительно | Обратных ссылок нет, но Web и BLL сильно знают инфраструктуру |
| Чистота Domain | Слабо | Прямая зависимость от Identity EF Core |
| Граница BLL | Удовлетворительно | Есть DTO и сервисы, но валидация и Identity разделены с Web |
| DAL и модель данных | Требует исправлений | Ошибка ключа OrderItems и недостаток ограничений |
| Безопасность | Требует срочных исправлений | Seed-пароль, Admin OrderController, путь удаления файлов |
| Тестируемость | Слабо | Тестовых проектов нет, BLL связан с DAL/Identity |
| Поддерживаемость | Удовлетворительно | Структура ясная, но есть дублирование и непоследовательные контракты |

Общий вывод: решение имеет хорошую учебную основу классической слоистой архитектуры, но пока не обеспечивает строгую изоляцию слоёв. До расширения функциональности желательно сначала устранить проблемы безопасности и модели данных, затем укрепить BLL как самостоятельную границу приложения и покрыть ключевые сценарии автоматическими тестами.
